# 智能面试辅助平台设计规格

## 1. 项目目标

构建一个可以在 Windows 本地运行的 AI 面试辅助平台，帮助求职者根据简历和目标岗位进行模拟面试，并得到结构化的评分、反馈和改进建议。

项目重点不是训练大模型，而是展示一个完整、可解释、可验证的 AI 应用流程：文档解析、检索增强、结构化输出、业务状态管理和前后端联调。

## 2. 用户与使用场景

第一版只面向单个求职者，不做注册、登录和多人协作。

典型流程如下：

1. 用户输入目标岗位描述，上传 PDF 或 DOCX 简历。
2. 系统提取简历和岗位描述的文本内容。
3. 系统分析岗位要求，生成不同难度和类型的面试题。
4. 用户逐题输入答案。
5. 系统按照统一评分标准评价答案，并给出改进建议。
6. 用户查看本次面试报告和历史记录。

## 3. 技术决策

采用以下方案作为默认实现：

- 后端：Python 3.11+、FastAPI、Pydantic、SQLAlchemy。
- 前端：React、Vite、基础 CSS。
- 数据库：SQLite，避免本地部署依赖 MySQL 服务。
- 文档解析：PyMuPDF 解析 PDF，python-docx 解析 DOCX。
- 检索：文档分块后使用轻量 TF-IDF 相似度检索，封装成独立 Retriever 接口；后续可以替换为向量模型而不改业务层。
- 大模型：OpenAI 兼容接口，默认支持 DeepSeek，也支持通过环境变量切换到 OpenAI 兼容服务或本地 Ollama。
- 测试：pytest、FastAPI TestClient；测试使用 FakeLLMProvider，不依赖真实 API 和网络。

选择轻量检索而不是直接引入复杂向量数据库，是为了降低 Windows 安装和调试成本，同时保留检索增强生成的核心思想和可解释性。

## 4. 功能范围

### 4.1 文档管理

- 接收 PDF、DOCX 和纯文本岗位描述。
- 限制文件类型和大小，拒绝空文件及无法解析的文件。
- 抽取文本并保存原始文件元信息和解析结果。
- 对文本进行分块，保留来源文档和块序号。

### 4.2 岗位分析

- 提取岗位名称、核心技能、工作职责和经验要求。
- 使用 Pydantic 模型校验大模型返回结果。
- 返回结构化岗位摘要，解析失败时给出可理解的错误提示。

### 4.3 智能出题

- 根据岗位要求、简历内容和检索到的相关片段生成题目。
- 题目类型至少包括基础知识、项目经历和场景分析。
- 题目包含难度、考察点、参考方向和排序号。
- 默认生成 5 道题，允许用户重新生成本次题目。

### 4.4 答案评价

- 用户逐题提交文字答案。
- 系统从准确性、完整性、岗位相关性和表达清晰度四个维度评分，每项 0 到 10 分。
- 系统返回总分、优点、问题、改进建议和可参考的回答结构。
- 评分结果必须经过数据模型校验，分数超出范围时不能直接写入数据库。
- 对上传文档中可能出现的指令性文字，仅作为求职资料处理，不能覆盖系统评价规则。

### 4.5 报告与历史

- 展示总分、分项得分、薄弱能力和逐题反馈。
- 保存面试会话、题目、答案和报告。
- 首页展示历史面试列表，可进入详情页查看报告。

## 5. 明确不包含的内容

第一版不实现以下功能：

- 语音识别、视频面试和摄像头监控。
- 在线搜索岗位信息。
- 复杂用户权限、支付和多人租户。
- 模型训练、微调和自建大模型服务。
- Docker、云服务器、Kubernetes 和生产级高可用部署。
- 直接复制开源项目的完整代码或把开源项目包装成个人原创。

这些内容可以作为后续迭代方向，但不影响第一版验收。

## 6. 核心数据结构

### interview_sessions

- `id`：会话 UUID。
- `job_title`：岗位名称。
- `job_description`：岗位描述文本。
- `resume_document_id`：关联简历文档。
- `status`：created、in_progress、completed、failed。
- `created_at`、`updated_at`：时间。

### documents

- `id`：文档 ID。
- `filename`：原文件名。
- `content_type`：文件类型。
- `text_content`：解析后的文本。
- `created_at`：创建时间。

### document_chunks

- `id`：分块 ID。
- `document_id`：来源文档。
- `chunk_index`：分块顺序。
- `content`：分块文本。
- `keywords`：用于检索的关键词信息。

### questions

- `id`：题目 ID。
- `session_id`：所属会话。
- `question_text`：题目内容。
- `question_type`：题目类型。
- `difficulty`：难度。
- `focus_points`：考察点。
- `reference_direction`：参考回答方向。
- `order_index`：题目顺序。

### answers

- `id`：答案 ID。
- `question_id`：所属题目。
- `answer_text`：用户答案。
- `score_json`：四项分数和总分。
- `feedback_json`：评价结果。
- `created_at`：提交时间。

### reports

- `id`：报告 ID。
- `session_id`：所属会话。
- `total_score`：总分。
- `summary`：总体评价。
- `weaknesses_json`：薄弱项。
- `recommendations_json`：改进建议。

## 7. 后端接口草案

- `GET /api/health`：检查服务是否正常。
- `POST /api/interviews`：创建面试会话并上传简历、岗位描述。
- `GET /api/interviews`：获取历史面试列表。
- `GET /api/interviews/{session_id}`：获取会话详情。
- `POST /api/interviews/{session_id}/questions`：生成面试题。
- `POST /api/questions/{question_id}/answers`：提交答案并获取评分。
- `GET /api/interviews/{session_id}/report`：获取面试报告。

接口统一返回明确的错误信息，文件错误、AI 服务错误和业务状态错误分开处理。

## 8. AI 服务边界

业务层不直接依赖某一家模型服务，而是依赖以下抽象接口：

- `analyze_job()`：岗位结构化分析。
- `generate_questions()`：根据上下文生成题目。
- `evaluate_answer()`：按照评分标准评价答案。
- `build_report()`：汇总面试结果。

真实模型适配器负责调用外部 API；FakeLLMProvider 返回固定、合法的测试数据。所有模型输出先经过 Pydantic 校验，再进入业务流程。

## 9. 测试与验收标准

### 自动化测试

- 文档解析：支持格式、空文件、损坏文件和超大文件。
- 检索模块：分块、关键词匹配和无结果处理。
- 业务状态：会话只能按合法状态流转。
- AI 输出：合法 JSON 能解析，非法分数和缺少字段会被拒绝。
- API 流程：创建会话、生成题目、提交答案、查看报告可以串联完成。
- 测试不调用真实大模型，不需要 API 密钥。

### 手工验收

使用一份测试简历和一份测试岗位描述，完成以下闭环：

`上传资料 → 创建会话 → 生成 5 道题 → 提交答案 → 查看评分 → 查看历史报告`

验收时需要确认：前端页面可操作、错误提示清晰、刷新后数据仍在、没有把 API 密钥提交到代码仓库。

## 10. 简历呈现原则

项目完成后，只填写实际完成并测量过的内容。例如：

“基于 FastAPI、React 和大语言模型实现智能面试辅助平台，完成简历/岗位文档解析、检索增强出题、结构化答案评分和面试报告生成；通过模型适配器与 FakeLLMProvider 分离真实调用和自动化测试。”

不使用“自主训练大模型”“达到某准确率”等无法提供证据的表述。后续如果加入评测数据，再补充实际的解析成功率、检索命中率或接口响应数据。

## 11. 完成定义

当以下条件全部满足时，第一版视为完成：

1. 项目目录结构清晰，前后端可以按 README 在本地启动。
2. 核心闭环可以成功运行。
3. 自动化测试全部通过。
4. 真实模型不可用时，系统能给出提示，测试仍可运行。
5. 关键错误和文件限制已处理。
6. 代码、配置示例、测试资料和简历项目描述齐全。
